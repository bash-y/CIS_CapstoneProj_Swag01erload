1. What the dashboard is

The dashboard is one web page that shows the state of your team project: what each layer of your software stack has finished, which pull requests are ready, which build tests failed, how far each milestone has come, and how many commits each teammate has made.

You never edit the page by hand. A small Python script reads your GitHub repository and writes the numbers into a file called data.js. The page reads that file and draws the panels.

Issues, pull requests, workflow runs, commits on GitHub→ scripts/generate_dashboard.py→ data.js→ index.html (the dashboard)

2. Start your team repository

One teammate does these steps once for the whole team.

  1. Open the template repository on GitHub and press Use this template, then Create a new repository.
  2. Set the Owner your instructor gave you, name the repository after your project, and choose the visibility your instructor asked for. Public repositories can publish the dashboard with GitHub Pages; private ones download it instead (see section 6).
  3. In the new repository open Settings, Collaborators and teams and add every teammate with the Write role.
  4. Each teammate clones it: 
    git clone https://github.com/OWNER/REPOSITORY.git
cd REPOSITORY
  5. Each teammate checks that their commits will be counted (see section 10): 
    git config user.email
    The address printed must be one of the emails on your GitHub account.

3. Define your layers

A layer is one part of your software that a teammate can own: the web pages, the API, the database, the login system. Your team chooses its own layers, but every layer must sit on a stack tier, one of the nine standard levels of a software stack below. That rule keeps every team's dashboard comparable, and it makes you say where each part of your code lives.

The nine stack tiers, top of the stack first
stack_tierMeaningExample layers
presentationWhat the user sees and touches.React app, mobile screens, command-line output
applicationBusiness rules and services.REST API, Flask routes, background jobs
integrationConnections to other systems.Payment API, webhooks, message queue
dataWhere information lives.PostgreSQL schema, file storage, ETL pipeline
securityIdentity, access, secrets, hardening.Login and roles, TLS, secret management, firewall rules
platformWhere the software runs.Docker, virtual machines, cloud account, network
deliveryHow changes ship.GitHub Actions, release scripts
qualityHow you know it works.Test suite, linters, vulnerability scanner
observabilityHow you see it running.Logs, metrics, alerts

Rules the build tests enforce

  • Between 3 and 12 layers, covering at least 3 different stack tiers.
  • Each id is lowercase letters, digits and single hyphens, like web-ui. It becomes the label layer:web-ui.
  • Each layer lists at least one real technology it is built with.
  • Two layers may share a tier. A security-focused team might have auth and secrets, both on security.

Example: a web application with login

presentation web-app: React, Vite
application api: Python, Flask
data database: PostgreSQL
security auth: OAuth 2.0, bcrypt
platform infra: Docker Compose

Edit dashboard.config.json. One layer looks like this:

{
  "id": "api",
  "name": "REST API",
  "stack_tier": "application",
  "description": "Endpoints that receive requests from the web app and apply the business rules.",
  "technologies": ["Python", "Flask"],
  "path": "api",
  "build": "pip install -r requirements.txt",
  "test": "python -m pytest -q"
}

path, build and test are for build tests and can stay empty until that layer has code (see section 8). Check your file before you commit it:

python3 scripts/generate_dashboard.py --check

On Windows use py in place of python3 in every command in this guide.

Commit and push the config. The Labels sync workflow then creates one layer: label per layer, plus type:story, type:task, type:bug and priority:P1 to P3. To create them by hand instead:

python3 scripts/sync_labels.py

5. Track work: labels, issues, stories

The dashboard only knows what you record on GitHub. Use this flow for every piece of work:

  1. Milestone. Under Issues, Milestones create one milestone per sprint or deliverable.
  2. Story. Open an issue with the Story template for each user-visible goal. It gets type:story. Add its layer: label, a priority and the milestone.
  3. Sub-issues. On the story press Create sub-issue for each task. The story's progress bar counts closed sub-issues.
  4. Branch and pull request. Work on a branch, open a pull request, write Closes #12 in its description, and add a layer: label. The Layer label check fails until you do.
  5. Review and merge. A teammate reviews. When build tests are green and the review is approved, merge. The issue closes and the layer's progress goes up.
Work with no layer label does not count. The dashboard lists unlabeled issues and pull requests in an Unassigned work note so you can fix them.

6. The refresh workflow

The file .github/workflows/dashboard-refresh.yml is already in your repository. It rebuilds the dashboard every 6 hours, on every push to main, and whenever you press Run workflow. The Refresh now button on the dashboard opens that page.

Turn on publishing

  1. Public repository: open Settings, Pages and set Source to GitHub Actions. Then open Actions, Dashboard refresh, Run workflow. When it finishes, the dashboard is at https://OWNER.github.io/REPOSITORY/.
  2. Private repository: a free GitHub organization cannot publish Pages from a private repository. Open the latest Dashboard refresh run, download the dashboard artifact, unzip it and open index.html. Or build it on your computer (section 7).

What each step does

If you ever need to rebuild this workflow yourself, or add one to another repository, this is the whole of it. Create .github/workflows/dashboard-refresh.yml with these parts:

name: Dashboard refresh

on:
  schedule:
    - cron: "23 */6 * * *"     # every 6 hours, at 23 minutes past (times are UTC)
  workflow_dispatch:            # adds the "Run workflow" button
  push:
    branches: [main]            # rebuild after every merge

permissions:                    # the built-in token may only read, plus publish Pages
  contents: read
  issues: read
  pull-requests: read
  checks: read
  actions: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4                 # 1. get the repository
      - uses: actions/setup-python@v5             # 2. install Python
        with: { python-version: "3.12" }
      - run: python3 scripts/generate_dashboard.py --out _site   # 3. read GitHub, write the site
        env:
          GH_TOKEN: ${{ github.token }}           #    the run's own short-lived token
      - uses: actions/upload-artifact@v4          # 4. keep a downloadable copy
        with: { name: dashboard, path: _site }
      - uses: actions/upload-pages-artifact@v3    # 5. hand the site to Pages
        with: { path: _site }
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: { name: github-pages }
    steps:
      - uses: actions/deploy-pages@v4             # 6. publish it

The version in your repository adds three safety steps: it validates the config first, runs the unit tests against the freshly built data, and only deploys when Pages is turned on.

Why no personal token is needed. Every workflow run gets a temporary GITHUB_TOKEN that expires when the run ends. The permissions block limits it to reading. Never paste a personal access token into a workflow file.
Why nothing is committed back. The workflow publishes the site instead of committing data.js to main. That keeps your history clean and means branch protection (section 9) never blocks the refresh.

8. Build tests on GitHub

What they are

A build test is a command GitHub runs on a clean computer every time someone opens or updates a pull request. It installs your code from scratch, builds it, and runs your tests. If any command fails, the pull request shows a red X; if all pass, a green check.

What they are used for

  • Catch breakage before it reaches main. A teammate's change that breaks the API fails its own pull request, not everyone's next pull.
  • End "it works on my machine." The test computer has nothing installed except what your build commands install, so a missing dependency shows up immediately.
  • Make reviews faster. The reviewer knows the code builds and the tests pass before reading a line.
  • Keep main always runnable, so a demo can happen at any moment.
  • Leave evidence. Every run is logged, and the dashboard shows which pull requests are green and which runs failed.

What runs in your repository

Jobs in .github/workflows/build-tests.yml
JobWhat it checks
dashboard-checksThe config follows the layer rules, the dashboard builds, and the unit tests in tests/ pass.
layer-tests (name)One job per layer that has a test command. It goes into the layer's path, runs build, then test.
all-greenOne summary result: passes only if every job above passed or was skipped. This is the one you make required.

path is the folder holding that layer's code, relative to the repository root, for example api or frontend. Leave it empty for the root.

Write a first test

A test is code that runs your code and checks the answer. For a Python API layer, create api/test_health.py:

from app import app

def test_health_endpoint_answers():
    client = app.test_client()
    response = client.get("/health")
    assert response.status_code == 200

Run it on your computer first (python -m pytest -q inside api). When it passes locally, push. GitHub runs the same command.

Read a failed test

  1. On the pull request, press Details next to the red check.
  2. Open the step with the red X. The last lines of the log say what failed.
  3. Run the same command on your computer, fix it, commit, and push again. The checks run again on their own.
Never make a test pass by deleting it. If a test is wrong, fix the test in its own commit and explain why in the pull request.

9. Make tests required

A failing test only protects main if GitHub refuses to merge while it fails.

  1. Merge one pull request first, so GitHub has seen the checks run at least once.
  2. Open Settings, Rules, Rulesets, New ruleset, New branch ruleset.
  3. Name it protect main, set Enforcement status to Active, and under Target branches add Include default branch.
  4. Tick Require a pull request before merging with 1 required approval.
  5. Tick Require status checks to pass and add all-green and layer-label.
  6. Tick Block force pushes, then Create.

Rulesets on private repositories need a paid plan. If the option is missing, agree as a team never to merge a red pull request; the dashboard shows it as Needs attention either way.

10. Commits by member

The last panel of the dashboard lists each teammate with:

  • commits on the default branch, all time and in the last 90 days;
  • a bar for each of the last 12 weeks, so a burst the night before a deadline is easy to see;
  • lines added and removed, pull requests opened and merged, and assigned issues closed;
  • the date of the last commit;
  • a share bar showing each person's part of all commits.

Make sure your commits are counted

GitHub matches a commit to a person by the commit's email address. If your laptop uses an email that is not on your GitHub account, your commits appear under your computer's user name with the flag Email not linked to GitHub, and they are missing from your row.

git config --global user.name  "Your Name"
git config --global user.email "the-email-on-your-github-account@example.com"

To keep your address private, use the noreply address shown in GitHub Settings, Emails. Commits already made with the wrong address count again once you add that address to your GitHub account.

What the numbers mean, and what they do not

  • Only commits that reach the default branch count. Work sitting on a branch appears once its pull request is merged.
  • A squash merge counts as one commit by the pull request's author.
  • Lines changed come from GitHub's contributor statistics. GitHub computes them in the background, so they can lag one refresh behind.
  • Many small commits are not better than a few good ones. Commit whenever one step works, with a message that says what changed.
  • A member flagged No commits in 90 days may be doing design or testing work; record that work in issues assigned to them.

12. Setup checklist

  • Repository created from the template, every teammate added with Write access.
  • dashboard.config.json has your project, every member and your own layers, and --check passes.
  • Labels exist (Labels sync ran green).
  • Every teammate's git config user.email is on their GitHub account.
  • At least one milestone and one story with sub-issues.
  • Pages turned on, or the team knows where to download the artifact.
  • Dashboard refresh ran green and the Sample data banner is gone.
  • Each layer with code has path, build and test filled in.
  • Ruleset requires all-green and layer-label before merging.
